On acceptance of this brief, PLAN.md section 4.8's "PR integration for GitHub, GitLab and Azure DevOps" becomes "PR integration for GitHub, GitLab, Azure DevOps, Forgejo and Gitea (Codeberg), and Tangled"; this brief edits that line. One forge trait serves all five families; the windows and commands use the forge's own names where they differ (merge request, work item) only in text the person reads, never in command ids.

## Goal

Eludite knows which forge a repository's remote lives on and works with it from inside the IDE and from the agent's commands, with the same depth on each of the five families where the forge offers it. The Git Changes window's "Create a Pull Request" link (Visual Studio's, shown after a push) opens a Create Pull Request form prefilled from the branch's commits. The Pull Requests window lists the repository's pull requests (mine, review requested, all; filter), and opening one shows its description, commits, files changed with Compare-style diffs, review threads anchored to lines in the editor's margin, checks with their logs, and the actions the forge allows: comment, start and submit a review (approve, request changes, comment), check out the branch, update after a push, mark ready, merge (merge, squash or rebase as the forge offers), close. The Issues window lists, filters, opens, creates, comments on, labels, assigns, closes and reopens issues, and creates a branch from an issue. Checks show per commit in the Pull Requests window and on the status bar for the current branch, with a run's log opened in a document and a rerun where the forge allows it. Every one of these is a command (`eludite.forge.*`) with a schema, so an agent lists the review comments on its pull request, answers them, pushes, and asks for a re-review through the same bus the person uses, under the policy's `forge` object. Sign-in is per forge host, tokens are kept in the operating system's credential store, nothing is fetched at startup, and everything read is cached so the windows open offline with what they last saw.

The five families, as this brief understands them at the time of writing; the first step of the brief verifies each against the live service and records corrections in the report:

- **GitHub** (github.com and GitHub Enterprise Server by host): REST API v3 and GraphQL where REST lacks a feature (review threads' resolution, the merge queue); authentication by the device flow of an OAuth App whose client id the owner registers (a build-time constant; the device flow needs no secret), by a personal access token pasted into the sign-in dialog, or by the token the `gh` CLI already holds (`gh auth token`, a process started only at sign-in, never on a hot path); checks are check runs and commit statuses; GitHub Actions runs and job logs.
- **GitLab** (gitlab.com and self-managed instances by host, detected by `GET /api/v4/version` or `/api/v4/metadata`): the REST API v4, GraphQL where REST lacks a feature (discussion resolution on diffs, the merge train); merge requests are this brief's pull requests, with approvals (approval rules where the instance has them), diff discussions anchored to lines, draft merge requests, merge methods (merge commit, fast-forward, semi-linear as the project allows), squash on merge, merge when pipeline succeeds; issues with labels, milestones, assignees, weight; pipelines and jobs as checks with job logs and retries; authentication by a personal access token pasted into the sign-in dialog, by the OAuth device flow where the instance supports it (an application id the owner registers; the flow needs no secret), or by the token the `glab` CLI holds (`glab auth token`, a process started only at sign-in).
- **Azure DevOps** (dev.azure.com organizations and Azure DevOps Server by host): the REST API (the pinned version, `api-version` on every call); pull requests with threads anchored to lines and iterations, reviewer votes (approve, approve with suggestions, wait for author, reject) as this brief's review submissions, completion with merge strategies (no fast-forward, squash, rebase, rebase and merge), auto-complete, draft pull requests, policies reported as checks (build validation, required reviewers, work item linking); work items are this brief's issues (the project's process decides the types; the Issues window lists the type and shows the fields the type has); pipelines (builds and runs) as checks with logs and reruns; branch from work item with the link recorded; authentication by a personal access token pasted into the sign-in dialog or by the Microsoft identity device code flow with an application id the owner registers (the token refreshed through the credential store); the `az` CLI is not used.
- **Forgejo and Gitea** (codeberg.org and any instance by host, detected by `GET /api/v1/version`): the REST API at `/api/v1` (the Swagger description is pinned); authentication by an access token pasted into the sign-in dialog, or OAuth2 with PKCE where the instance has an application registered for Eludite (optional); pull requests, reviews, issues, labels, milestones, commit statuses; Forgejo Actions runs and logs where the instance enables them.
- **Tangled** (tangled.sh and self-hosted knots): a forge on the AT Protocol: repositories live on knots (git servers run by users or the service), records (repositories, issues, pull requests, comments) live in the user's personal data server under the `sh.tangled.*` lexicons, and the appview at tangled.sh indexes them; authentication by an atproto session (`com.atproto.server.createSession` with an app password pasted into the sign-in dialog; atproto OAuth later); pull requests and issues through the lexicons, CI through spindles where exposed. The lexicon set is pinned from Tangled's source at a commit. If, during the first step, pull requests or reviews turn out not to be reachable through stable lexicons or an API, the Tangled part of this brief is reduced to what is reachable (repositories, issues, clone, the account) and the report says exactly what was missing; that is a legitimate exit for the Tangled part, not for the other four.

## Contract

- **Detection and capabilities.** `forge.detect` (read) answers from the remote url and `forge.hosts` with the family, host, owner and repository (organization, project and repository for Azure DevOps; group path and project for GitLab), the signed-in account, and the capabilities; the windows and the menus enable only what the capabilities allow; an unknown host answers `family: none` and the windows show "No supported forge for <remote>". Detection runs when a window opens or a command asks, never at startup.
- **Sign-in.** Per host; the token goes to the credential store and never to a log, an audit entry, a command output or the cache; `sign_out` removes it; an agent's call that needs a token when none is stored is refused with `sign_in_required` and the host; `sign_in` from an agent is refused outright.
- **Reads.** Every list is paged (`max` default 50, cap 200, a cursor) and cached; a read answers from the cache at once with `stale: true` and the age while a refresh runs off-thread, then the window updates; a failed refresh keeps the cache and says why (rate limit with the reset time, network, authorization). The description, comments and review bodies render as Markdown (brief 0043's renderer) with links clickable and images fetched only on demand.
- **Pull requests.** Create from the current branch with the form; `pull_checkout` fetches `refs/pull/<n>/head` (GitHub, Forgejo and Gitea), `refs/merge-requests/<n>/head` (GitLab), `refs/pull/<n>/merge` or the source branch (Azure DevOps), or the head branch from its repository (forks, Tangled) into a local branch `pr/<n>` (or the forge's convention) and checks it out through brief 0040's path with the dirty-tree rule; review threads anchor to the file and line of the head commit and the editor shows them in the margin on the checked-out branch, with a popover to read the thread and reply; a review collects pending comments and submits them in one call where the forge supports pending reviews, else each comment posts at once and the submit posts the summary; `merge` is `dangerous` with a confirmation naming the method and refuses when the forge reports the pull request unmergeable or checks failing unless `force` (never for agents); close and reopen; mark ready; update the title, body and base.
- **Issues.** List with filters (open, closed, mine, assigned, labels, text); open shows the description and comments; create, comment, edit labels, assignees, milestone and state where the forge supports them; "Create branch from issue" creates `issue/<n>-<slug>` through brief 0040 and records the link in the forge where it supports linking (GitHub's development panel; GitLab's related branch; Azure DevOps' work item branch link; Forgejo's branch reference; Tangled by a comment).
- **Checks.** Per commit: name, status, conclusion, url, duration; the current branch's head commit's checks in the status bar as one glyph and a count; a log opens as a read-only document (capped at 2 MB, the rest by url); rerun where allowed (`execute`).
- **Policy and audit.** Reads are `read`; writes are `execute` under `forge.write` (`prompt` by default, so an agent's first comment asks and "Allow for this session" holds as brief 0041 does); merge and close are `dangerous` under `forge.merge` (`deny` by default for agents); every write is audited with the forge, the repository, the pull request or issue number and the body's length, never the token.
- **Agents' loop.** `pull` with `threads: unresolved` answers the review threads an agent must address with their file, line and body; `pull_comment` with `reply_to` answers a thread; `thread_resolve` where the forge supports it; `pull_review` with `request` re-requests the reviewer; `eludite://forge/pull/current` is the pull request of the current branch; the guide shows the loop in four calls.
- **Invariants.** No network at startup; the UI thread never waits on the network (every call runs on the forge worker with a cancellation token and a generation per repository, stale answers dropped); no process is started except `gh auth token` or `glab auth token` at sign-in when the person chooses that method; the credential store is the only place a token lives; the cache holds no secret; nothing of a forge's API is called by the shell outside `crates/forge`.
- Commit messages: one plain, direct, active-voice line each; no body, no trailers.

## Budget

- A cached list renders within 50 ms of the window opening; a refresh of 50 pull requests completes within 2 s on a normal connection (measured against the fixture server with an injected 20 ms per request, and reported from the owner's real runs).
- The pull request document with 100 files and 300 threads opens within 200 ms from the cache and keeps frame p99 under 8 ms while scrolling (virtualized; `assert_budget`).
- Shell memory with both windows open and the cache of a 500-pull-request repository loaded: under 40 MB more.
- Dependencies: `keyring` (MIT OR Apache-2.0) and what its Linux backend needs, listed in the PR with SPDX ids; `ureq` and `rustls` are already in the build and become direct dependencies of `crates/forge`; no other new crate.
