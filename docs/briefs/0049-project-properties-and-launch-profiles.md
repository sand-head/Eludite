# Brief 0049: Project property pages, launch profiles, and the configuration and platform selectors

Status: open

## Goal

Double-click a project (or Project > Properties, Alt+Enter on a project) to open Visual Studio's project property pages as a document tab: Application (assembly name, default namespace, target framework or frameworks, output type, startup object, nullable, implicit usings, language version, Win32 resources off Windows shown read-only), Build (general: conditional compilation symbols, warning level, treat warnings as errors, specific warnings, XML documentation; output: output path, base output path; events: pre-build and post-build commands; strong naming; advanced: deterministic, debug type), Package (package id, version, authors, description, license, project url, readme, repository, tags, generate package on build), Debug (opens the launch profiles UI), Code Analysis (enforce code style on build, analysis level), Resources, Settings and Signing listed with "not yet" text where unimplemented. Each page edits the project file through the host, preserving formatting, with the Configuration and Platform lists at the top of the pages that are conditional, writing a conditioned property group only when the value differs per configuration, as Visual Studio does. The Debug page is the launch profiles editor over `Properties/launchSettings.json`: the profile list, New, Delete, Rename, and per kind (Project, Executable, IIS Express listed read-only off Windows) the command line arguments, working directory, environment variables table, `launchBrowser`, `launchUrl`, `applicationUrl`, `dotnetRunMessages`, `hotReloadEnabled`; the Debug toolbar's profile dropdown picks the profile F5 uses. The Standard toolbar gains the Solution Configurations and Solution Platforms lists (Debug, Release and the solution's own; Any CPU, x64, x86, ARM64 and the solution's own) with Configuration Manager (the solution-to-project mapping grid, editing the solution file), and Build, Debug and Test use the selection; a multi-targeted project shows a Target Framework list in the editor's navigation bar and in the Debug toolbar, and launch and Test Explorer use it. Agents get `eludite.project.properties` (read), `eludite.project.set_property` (execute, with the configuration and platform condition), `eludite.project.launch_profiles` and `eludite.project.set_launch_profile`, `eludite.solution.configurations` and `eludite.solution.select_configuration`, with the same semantics.

## Contract

- **Pages.** The catalog's properties, grouped as Visual Studio's pages; a value shows its source (the project, a conditioned group, an inherited file); an edit writes exactly one element change per property, preserving everything else byte-for-byte; Save writes all dirty pages in one host call per project file; the tree, IntelliSense and the build see the change through the generation (the host reloads the project).
- **Conditions.** A property marked per configuration shows the lists; a value entered for one configuration goes to that configuration's group; "All Configurations" writes the unconditioned value and removes the conditioned ones for that property after confirmation; defaults remove elements.
- **Launch profiles.** The file's order and unknown members survive; New creates a Project profile with the project's defaults; the Debug toolbar's dropdown and `debug.start`'s `profile` agree; a profile's `environmentVariables` edit keeps the table order.
- **Configurations and platforms.** The lists show the solution's own entries; selecting one persists per solution and applies to build, debug and tests (and to the Cargo path as profiles); Configuration Manager edits the mapping and the solution file preserving formatting; a project without a mapping for a selection is skipped on build as Visual Studio does, with an Output line.
- **Target frameworks.** A multi-targeted project's list drives `debug.start` and `test.run` with `framework`; the editor's navigation bar list switches the semantic context when the host supports it, else it changes only the launch and test target and says so in the report.
- **Agents.** `properties` answers the catalog with values and sources; `set_property` with a configuration or platform follows the same rule; `launch_profiles` and `set_launch_profile`; `configurations` and `select_configuration`; all audited; `set_property` is `execute`.
- The UI thread never waits on the host; the host's stdout stays protocol-only; every call carries the generation.
- Commit messages: one plain, direct, active-voice line each; no body, no trailers.

## Proving test

- `dotnet/tests`: the corpus round trips; every catalog property; the condition rule with and without existing groups; the inherited rule; launch profiles with unknown members and ordering; `.sln` and `.slnx` configuration mapping edits; the second evaluation per configuration; cancellation.
- `crates/eludite` headless tests (fake host): the pages open from the tree and the menu, show values with sources, an edit marks dirty and Save writes through the host and advances the generation, close prompts, the Configuration and Platform lists change the shown values and route the write, All Configurations confirms, the inherited banner's Override, the launch profiles page edits a profile and F5 uses it, the toolbar lists select and persist and the build uses the selection, Configuration Manager edits the mapping, a project skipped by the mapping writes the Output line, the Target Framework list drives a start and a test run, an agent's `properties` and `set_property` match the pages.
- Real host: a property edit and a launch profile edit on a copy of a corpus project through the real host.
- The Xvfb run's screenshots in the report.

## Budget

- The pages open in under 150 ms for a 30-property project (the evaluation cached per generation); Save under 300 ms plus the host's reload.
- The Configuration list change re-evaluates in under 500 ms for a 100-project solution (off-thread, the toolbar never waits).
- No new dependency.

## Exit criterion

1. `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` green; `dotnet build` zero warnings and `dotnet test` green with the property tests running on the corpus.
2. The report records the catalog as shipped, the condition and inherited rules, the budget numbers, what the navigation bar's framework switch does, and what the remaining pages (Resources, Settings, Signing) need.
3. `CLAUDE.md`, `README.md` if touched, `corpus/README.md` and the briefs index match the repository.

## Out of scope

- Resources, Settings and Signing pages (listed with "not yet"); `.resx` and `.settings` editors (PLAN.md 4.11, later briefs); IIS Express profiles beyond read-only; legacy non-SDK project files (shown read-only with a note); Windows and macOS runs beyond CI.
