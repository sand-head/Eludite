# Brief 0022: The Mono soft-debugger adapter, so .NET Framework programs debug on Linux and macOS

Status: done on Linux (Windows and macOS not run); [report](0022-report.md)
Phase: 2 (proposal 0001, brief E1)
Plan reference: PLAN.md sections 2 (principles 1, 2, 3, 5), 3 (D3, D7), 4.5 (cross-platform .NET Framework debugging, option 2), 5.5, 6, 9, 10 (Phase 2); proposal 0001 sections 6 and 8 (E1)
Related ADRs: ADR-0002, ADR-0003, ADR-0007
Depends on: briefs 0018 (debugging), 0020 (settings, F5 builds first); builds on brief 0003's Mono discovery

## Goal

F5 on a project that targets .NET Framework runs it under Mono on Linux and macOS, with every debugger window, key and `eludite.debug.*` command of brief 0018 working unchanged, through a new DAP server, `eludite-dbg-mono`. The server is a C# program on Mono.Debugging.Soft (MIT, mono/debugger-libs, the library MonoDevelop and vscode-mono-debug debug with) that runs under the located Mono and launches the debuggee as `mono --debug --debugger-agent=...`. The shell picks the adapter from the project's target framework and the platform: netcoredbg for .NET (Core) 5+ as today, `eludite-dbg-mono` for .NET Framework off Windows, and on Windows a clear message that .NET Framework debugging there is `eludite-dbg-netfx` (brief 0004). Mono is located, never bundled (PLAN.md D4, brief 0003), and the adapter is a DAP server that does not assume a local client (D7: stdio and TCP).

What was established before this brief (a spike on 2026-10-02, Ubuntu 24.04, Mono 6.8.0.105 from the distribution): the NuGet packages `Mono.Debugging.Soft`, `Mono.Debugging` and `Mono.Debugger.Soft` 1.0.20170212.42 (MIT; dependencies `Mono.Cecil` 0.9.6 and `ICSharpCode.NRefactory` 5.5.1, both MIT) work under Mono: a net472 program referencing them launched a Mono program, resolved a pending breakpoint and hit it 204 ms after `Run`, read the locals of two frames, stepped over a line, evaluated `greeting.Length` and ran to exit. They do not work on .NET 10: `Mono.Debugger.Soft` uses delegate `BeginInvoke` internally (`PlatformNotSupportedException` on the first asynchronous command), so the adapter must run under Mono, which is always present when there is a Mono program to debug. Two things the spike learned that the implementation must do: set `DebuggerLoggingService.CustomLogger` before `Run` (the library dereferences it), and handle stops on `TargetEvent` (`TargetHitBreakpoint`, `TargetStopped`, `TargetExceptionThrown`, `TargetUnhandledException`, `TargetInterrupted`), not only `TargetStopped`. One evaluator gap seen: `a + b * 2` failed with "Value '3' of type System.Int32 cannot be casted to System.Int64" while identifiers and member access worked; the report lists what the evaluator handles. Upstream mono/debugger-libs targets `net6.0;net472` as of 2026 but publishes no packages; it is the path to an adapter running on .NET 10 later and is out of scope here.

## Contract

### The adapter

- `eludite-dbg-mono.exe` speaks DAP (1.65 or later) on stdio by default and on TCP with `--port N` (listens on loopback; `--port 0` prints the chosen port on stderr). Its stdout carries DAP only; logs go to stderr (invariant 10), with `--log FILE` as an option. It is started as `mono eludite-dbg-mono.exe [options]`.
- `initialize` (`adapterID` `mono`) answers these capabilities, each true only when implemented: `supportsConfigurationDoneRequest`, `supportsConditionalBreakpoints`, `supportsHitConditionalBreakpoints` (Mono.Debugging's hit count modes), `supportsFunctionBreakpoints`, `supportsLogPoints` (tracepoints through Mono.Debugging's `HitAction.PrintExpression`), `supportsEvaluateForHovers`, `supportsSetVariable`, `supportsExceptionInfoRequest`, `supportsExceptionFilterOptions` with `exceptionBreakpointFilters` `all` (first-chance: a catchpoint on `System.Exception` with subclasses, or on the `filterOptions` conditions' type names) and `user-unhandled` (default on), `supportsTerminateRequest`, `supportsDelayedStackTraceLoading` (`stackTrace` honors `startFrame` and `levels`, answers `totalFrames`). It sends a `capabilities` event after `initialize` only if something changes.
- `launch` arguments (documented in `dap-mono.md`): `program` (the `.exe`), `args` (array), `cwd`, `env` (object), `runtimeExecutable` (the `mono` to run the debuggee with; default: the Mono running the adapter, read from the current process), `runtimeArgs` (extra `mono` options), `stopAtEntry` (default false), `justMyCode` (default true: frames of assemblies without source are external code and steps do not enter them). `attach` arguments: `address` (default `127.0.0.1`) and `port`, connecting to a program started with `--debugger-agent=transport=dt_socket,server=y,...`. The debuggee's stdout and stderr become `output` events with categories `stdout` and `stderr`; the adapter's own messages use `console`.
- Requests: `initialize`, `launch`, `attach`, `setBreakpoints` (with `condition`, `hitCondition` as `N`, `>=N`, `%N` as the shell sends them, `logMessage` with `{expression}` interpolation), `setFunctionBreakpoints`, `setExceptionBreakpoints`, `configurationDone`, `threads`, `stackTrace`, `scopes` (one `Locals` scope holding `this`, parameters and locals, as the Locals window expects), `variables` (`start` and `count` paging; a variables reference per expandable value per stop, dropped when the debuggee resumes), `evaluate` (contexts `watch`, `hover`, `repl`; a failed `hover` is an error answer with no side-effect text), `setVariable`, `continue`, `next`, `stepIn`, `stepOut`, `pause`, `exceptionInfo`, `disconnect` (with `terminateDebuggee`), `terminate`. Unknown requests get a failed response naming the command, never a crash.
- Events: `initialized`, `stopped` (`reason` `breakpoint`, `step`, `exception`, `pause`, `entry`, `function breakpoint`; `threadId`; `description` and `text` for exceptions; `allThreadsStopped` true), `continued`, `thread` (`started`, `exited`), `breakpoint` (`changed` when a pending breakpoint binds, with `verified` and the bound line), `output`, `exited` (`exitCode`), `terminated`.
- Every request is answered from one dispatcher thread; Mono.Debugging callbacks post to it. The adapter never deadlocks on an evaluation that does not return: evaluations have a timeout (3 s default, `evaluate` argument `timeout` optional) and answer an error naming it.
- Values: `value` is Mono.Debugging's display string (strings quoted, objects as `{Type}` when they have no `ToString` override, arrays as `{string[3]}`), `type` the type name, `namedVariables` and `indexedVariables` when known so the shell pages big collections.

### The shell

- Target framework classification (`crates/dap/src/launch.rs`): `netcoreapp*`, `netstandard*` (not runnable) and `netN.M` with N >= 5 are CoreCLR; `net2*`, `net3*`, `net4*` (SDK-style) and a legacy project's `TargetFrameworkVersion` `v2.0` to `v4.8.1` are .NET Framework. A legacy project (no `Sdk` attribute) builds to `<OutputPath>` (default `bin\Debug\`, backslashes normalized) as `<AssemblyName>.exe`; an SDK-style .NET Framework project to `bin/Debug/<tfm>/<AssemblyName>.exe`. `output_program` finds the `.exe` for .NET Framework and the `.dll` for CoreCLR, with an error that names the first candidate when none exists.
- Adapter selection: CoreCLR uses netcoredbg (unchanged); .NET Framework on Linux and macOS uses `eludite-dbg-mono` under the located Mono; .NET Framework on Windows fails the start with "Debugging .NET Framework on Windows needs eludite-dbg-netfx (brief 0004), which is not built yet; on Linux and macOS Eludite debugs it under Mono" (no attempt to run Mono there). Start Without Debugging runs `mono <exe> <args>` off Windows and `<exe> <args>` on Windows for .NET Framework, `dotnet <dll>` for CoreCLR.
- Mono discovery (`crates/dap/src/discovery.rs`, the order brief 0003 fixed in `MonoInstallation.cs`): the setting `debugger.monoPrefix` (`ELUDITE_MONO_PREFIX`), then `mono` on `PATH` (its prefix is two directories up from the resolved executable), then `~/.local/opt/mono-root/usr`, `/usr`, `/usr/local`, `/Library/Frameworks/Mono.framework/Versions/Current`; a candidate counts when `<prefix>/bin/mono` exists. The adapter runs with brief 0003's environment for a relocated prefix (`PATH`, `LD_LIBRARY_PATH`, `MONO_CFG_DIR`, `MONO_GAC_PREFIX`). Adapter discovery: beside the `eludite` executable (`<exe dir>/eludite-dbg-mono/eludite-dbg-mono.exe`, then `<exe dir>/eludite-dbg-mono.exe`), then `debugger.monoAdapterPath` (`ELUDITE_DBG_MONO`, a file or its folder). The error for a missing adapter names both places and `dotnet build dotnet/Eludite.slnx`, whose output is `debuggers/mono/Eludite.Debugger.Mono/bin/Debug/net472/eludite-dbg-mono.exe`; for missing Mono it names the places searched and the distribution package (`mono-devel` on Debian and Ubuntu, `mono` on Arch, the Mono framework on macOS).
- `eludite.debug.state`'s `session.adapter` reads `eludite-dbg-mono under mono 6.8.0.105 (stdio)` (the version from `mono --version`'s first line, read once on the launch thread), `session.runtime` is `mono`; the status bar slot is unchanged in shape.
- The breakpoints, exception settings, watches, hit counts counted by the shell when an adapter lacks them, Run To Cursor, data tips and the two-driver rules are not changed; the adapter advertises hit conditions, so the shell hands them to it (the existing rule).
- Commit messages: one plain, direct, active-voice line each; no body, no trailers.

## Proving test

- `Eludite.Debugger.Mono.Tests` (xunit v3, net10.0), two groups:
  - Without Mono (always run): framing round trips; the dispatcher answers an unknown request with a failure; `launch` argument parsing with defaults; hit-condition parsing; `{expression}` interpolation in log messages; the variables-reference table pages `start` and `count` and is cleared on resume.
  - With Mono (skip with a message when `mono` is not found by the same search order): the tests start `mono eludite-dbg-mono.exe` over stdio and over `--port 0`, debug the built TestApp, and check: `initialize` capabilities; `launch` then `initialized`; `setBreakpoints` answers verified breakpoints (or binds them with a `breakpoint` event before the stop); `configurationDone`; `stopped` with reason `breakpoint` on the right line; `threads`, `stackTrace` (`totalFrames`, paging with `startFrame` 1), `scopes`, `variables` with `this`, parameters and locals, a `string[]` paged with `start` and `count`, an object expanded one level; `evaluate` of an identifier, a member chain and a method call in `watch` context and a failing `hover`; `setVariable` changes an int and the next `variables` shows it; `next`, `stepIn`, `stepOut` each produce `stopped` with reason `step` on the expected line; a conditional breakpoint that skips, a hit condition `%2`, a log point whose text arrives as `output` without a stop; a function breakpoint by `Namespace.Type.Method`; `setExceptionBreakpoints` with `all` stops at the caught throw with `exceptionInfo` giving the type and message, and without it the throw does not stop; `pause` while the TestApp sleeps gives `stopped` with reason `pause`; `disconnect` ends the debuggee and `terminated` arrives; `attach` to a TestApp started by the test with `--debugger-agent=...,server=y,suspend=y`. Timings: launch to the first `stopped` and 50 `next` round trips, written to the test output for the report.
- `crates/dap`: unit tests for the classification, the legacy and SDK-style output paths (temp projects), Mono and adapter discovery order (temp directories, as `search_order_is_bundled_env_path` does), the selection table including the Windows message, and the `launch` arguments. `crates/dap/tests/mono.rs`: the client against the real adapter debugging the built TestApp (launch, breakpoint, stack, locals, evaluate, step, continue, stop); skipped with a message unless Mono, the adapter and the TestApp are found.
- `crates/eludite` headless tests (fake adapter): a solution whose startup project targets `net472` sends the adapter a `mono` plan (`adapterID`, `program` ending in `.exe`, `runtimeExecutable`) and shows `runtime` `mono` in the state; Ctrl+F5 on it runs `mono`; the Windows message path (a test that forces the platform through a parameter rather than `cfg`); the settings `debugger.monoPrefix` and `debugger.monoAdapterPath` reach the search.
- No display: where brief 0018 ran the IDE by hand, this brief proves the flow with `cargo test -p eludite-dap --test mono` against the real adapter and says so in the report.

## Budget

- Launch to the first `stopped` at a breakpoint in the TestApp under 3 s warm (report cold too), measured by the integration test.
- `next` round trip under 150 ms p95 over 50 steps, measured by the integration test.
- `stackTrace` plus `scopes` plus `variables` for a frame with 200 locals under 100 ms, from the adapter.
- The adapter's resident memory at a break under 80 MB; the shell's unchanged.
- Cold start of Eludite unchanged: nothing of Mono is touched before F5.

## Exit criterion

1. `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` green; `dotnet build dotnet/Eludite.slnx` with zero warnings and `dotnet test dotnet/Eludite.slnx` green, with the Mono tests running (not skipped) on this machine.
2. The real-adapter tests pass on Linux with the distribution's Mono; the report records their timings against the budgets.
3. The report lists: how Mono and the libraries were obtained with SPDX ids; the DAP features the adapter lacks or emulates (as brief 0018's section 5); what the expression evaluator handles and fails on; the Mono.Debugging gaps found; and what brief A of proposal 0001 (inspection depth) needs from this adapter, if anything.
4. `CLAUDE.md`, `README.md` and the briefs index match the repository.

## Out of scope

- `eludite-dbg-netfx` and anything Windows-only (brief 0004).
- Building legacy (non-SDK) projects inside the IDE with Mono's MSBuild; F5's build-before-run uses the existing pipeline, and a failing build shows its reason as brief 0020 does. The proving projects are SDK-style `net472` projects, which `dotnet build` builds everywhere.
- Attach to Process dialog, process listing, `restart` (proposal 0001 brief C); `snapshot`, `stack` and `variables` as shell commands (brief A).
- Running the adapter on .NET 10 (needs upstream debugger-libs packages or a build from source).
- ASP.NET under XSP, Mono's `csharp` REPL, Edit and Continue, Set Next Statement (Mono.Debugging has `SetNextStatement`; leave it to brief B).
- Windows and macOS runs.
