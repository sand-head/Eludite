# Brief 0056: Razor highlighting from the in-repo tree-sitter grammar

Status: done (2026-10-05, Linux; Windows and macOS by CI)
Phase: 2 (PLAN.md section 10: "Razor/Blazor"; section 7, the Web row: "Razor and Blazor share this stack")
Plan reference: PLAN.md sections 2 (principles 1, 4, 6), 4.1 (syntax highlighting from tree-sitter), 4.9 (Razor and Blazor), 7, 8, 9, 10 (Phase 2), 11 (corpora)
Related ADRs: ADR-0001, ADR-0005 (the grammar is MIT, the owner's own library)
Depends on: brief 0050 (the language table `crates/editor/src/syntax/language.rs`, injections, Emmet, the HTML server on `.cshtml`), brief 0009 and 0011 (the editor's tree-sitter path and its allocator).

## Goal

A `.razor` or `.cshtml` file is highlighted at once by a Razor grammar: the directives, transitions, control structures and C# of Razor by the C# query the editor already has, the markup with its tag names, attribute names and values, the directive attributes (`@bind-Value`, `@onclick`, `@key`, `@ref`), and `<script>` and `<style>` bodies as JavaScript and CSS through the editor's injections. The grammar is the owner's `tree-sitter-razor` (MIT, forked from tris203/tree-sitter-razor, extending tree-sitter-c-sharp 0.23.5), brought into the repository as `grammars/razor/` with its generated parser checked in, its test corpus replayed by `cargo test` with no tree-sitter CLI, and the gaps real code found closed, so that the files of the Blazor, Razor Pages and MVC templates and of MudBlazor, dotnet/eShop and eShopOnWeb parse with no error nodes. The HTML server keeps serving `.cshtml` markup as brief 0050 left it, and `.razor` joins it. Language services for Razor (completion, diagnostics, navigation from the Razor language server cohosted with Roslyn) are a later proposal; this brief is the editor's half.

## Contract

**The grammar crate.**

- `grammars/razor` is a path dependency named `tree-sitter-razor`, MIT, with the generated `src/parser.c` and `src/scanner.c` checked in like every tree-sitter grammar crate on crates.io; `generate.sh` is the only way they change, with the CLI version in `PIN` (0.27.0 to match the editor's `tree-sitter` 0.27 runtime; ABI 15). `src/` is never edited by hand (CLAUDE.md invariant 4's rule for generated code applies). *Superseded on 2026-10-05 by the owner's decision on the pull request (ADR-0012): the parser is generated at build time from the checked-in `src/grammar.json` by the CLI's own generator at the same pin, cached by content; nothing generated beyond `grammar.json` is checked in.*
- `tests/corpus.rs` parses every case in `test/corpus/*.txt` and compares the root's S-expression (whitespace-normalized) with the case's expected tree, so `cargo test -p tree-sitter-razor` proves the grammar on every CI platform without Node or the CLI. A case marked `:error` in its header is expected to carry `ERROR` nodes.
- Every `razor_*` node and every `at_*` alias the library has today keeps its name, so the owner's library queries stay valid against this grammar.
- **Named nodes for highlighting**, added by this brief: `tag_name` (start and end tags, components included), `attribute_name`, `attribute_value` (the text of a quoted or unquoted value; the quotes stay anonymous), `text` (a run of markup text), `entity`, `script_element` and `style_element` with a `raw_text` child (their bodies are never parsed as markup), `razor_attribute_name` and `razor_attribute_modifier` as today. `doctype`, `html_comment` and `razor_comment` as today.
- **Gaps closed**, each with a corpus case: an implicit expression inside a directive attribute's value (`@bind-Value="@_dense"`, `@key="@item.Id"`, `@onclick="@Go"`); `@namespace` with a single identifier; a trailing `;` after `@using`, `@inherits`, `@implements`, `@inject`, `@model`, `@layout` and `@namespace`; a bare `@page` (Razor Pages) and `@page` with a route; preprocessor lines (`#nullable`, `#pragma`, `#region`, `#if`) inside `@code`, `@functions` and `@{ }` blocks; `@rendermode @(expression)`; dotted tag names (`<eShop.Components.CatalogSearch>`) and namespaced ones; an unquoted attribute value (`Attr=@expr`, `class=foo`); `<script>` and `<style>` bodies as `raw_text`; a leading BOM as an extra; markup text at the top level and directly inside `@if`, `@foreach`, `@section` and the other blended bodies; `T="@(int?)"` (a type as an explicit expression's content).
- Measured on real code (the report records it): the `.razor` and `.cshtml` files of MudBlazor, dotnet/eShop and eShopOnWeb at their current heads, and the files `dotnet new blazor`, `blazorwasm`, `razor` and `mvc` produce, parse with no error nodes; any file that still errors is listed in the report with the construct, and there are at most five such constructs. The 665-line `MudDataGrid.razor` parses in under 5 ms in release (it is 28 ms today because the attribute gap makes error recovery do the work).

**The editor.**

- `RAZOR` is one `LanguageConfig`: `highlights_query` is the C# query followed by `queries/razor/highlights.scm`; the Razor query captures `tag_name` as `@tag`, `attribute_name` as `@tag.attribute`, `attribute_value` as `@string`, `entity` as `@string.escape`, `doctype` as `@keyword`, `razor_comment` and `html_comment` as `@comment`, the `at_*` directive and transition aliases as `@keyword` (Visual Studio draws `@` and its keyword in the keyword color), `razor_attribute_name` as `@tag.attribute` with its `@` included; the injections query sends `script_element`'s `raw_text` to JavaScript and `style_element`'s to CSS; `emmet` is `EmmetSyntax::Html`. The Razor query goes after the C# one because the editor's rule is that the earlier pattern wins on the same node, and C# must win inside code.
- `for_path` maps `.razor` and `.cshtml` to `razor`; `.html` and `.htm` stay `html`. The HTML server's registration serves `.cshtml` and `.razor` with `languageId` `html` (markup completion in both; no Razor server yet). The LSP registry's language id for a document and the editor's language id are separate tables, as today.
- Highlighting stays within the editor's existing path: parsed and queried on the highlight worker, never on the UI thread; a Razor document's keystroke budget is the editor's (PLAN.md section 9); no new allocation pattern (the grammar's parser uses the editor's mimalloc arena like every other grammar).
- Commit messages: one plain, direct, active-voice line each; no body, no trailers.

## Proving test

- `cargo test -p tree-sitter-razor`: the corpus replay (every case, including the new ones for each gap) and the fixtures test (`corpus/web/razor/**` has no error nodes).
- `crates/editor/src/syntax/web_tests.rs`: `.razor` and `.cshtml` resolve to `razor`; on a Blazor component fixture the highlight kinds at known positions are `Keyword` for `@page`, `@if` and `@code`, `Tag` for a tag name and a component name, `AttributeName` for `class` and for `@bind-Value`, `String` for an attribute value, `Keyword` and `Type` inside `@code` from the C# query, `Comment` for `@* *@`; a `<script>` body gets JavaScript kinds and a `<style>` body CSS kinds through the injections; an edit in the `@code` block re-highlights without error nodes.
- `crates/lsp/src/registry.rs`: `.razor` and `.cshtml` go to the HTML server with `languageId` `html`.
- `crates/eludite/src/shell/web_tests.rs`: opening `Views/Home/Index.cshtml` shows Razor highlighting (a keyword kind at `@model`, a tag kind at `<h1>`) and the HTML server's completion; the same for `Components/Pages/Counter.razor`.
- The report: the real-code table (files, files with error nodes before and after, parse p50, p95, max), the generation command and its time, the parser's compile time and the shell binary's size delta, and the three repositories' commit hashes.

## Budget

- The editor's keystroke and highlighting budgets (PLAN.md section 9) unchanged on a Razor document; a 700-line component parses in under 5 ms in release and re-parses incrementally after an edit in under 1 ms.
- `cargo build` of `tree-sitter-razor` adds no more than 15 s to a cold build (the parser is a second C# parser: the library's is 57 MB of generated C compiling to an 11 MB static library); the release shell binary grows by no more than the parser's linked size, which the report measures (the brief first said 4 MB, a guess; a parser that embeds C# cannot be smaller than the C# grammar's own 5.3 MB object, and the report records 8.3 MB). *With ADR-0012 the cold build also generates the parser once per cache key (16 s measured, section 5 of the report), then copies it.*
- New dependency: `tree-sitter-razor` (path, MIT) and its `tree-sitter-language` (MIT, already in the build through the other grammars). No other.

## Exit criterion

1. `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` green on Linux here and on CI's three platforms.
2. The real-code table in the report shows zero files with error nodes on the four templates and at most five remaining constructs across MudBlazor, eShop and eShopOnWeb, each named.
3. `grammars/razor/README.md` says how to regenerate and lists every change from the library's `bed3116`, so the owner can carry them back upstream.
4. The briefs index, `corpus/README.md` and `CLAUDE.md`'s crate map match the repository.
