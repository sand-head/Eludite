## Goal

The files an ASP.NET Core developer edits every day besides C# work as they do in Visual Studio and Rider: project files, `web.config`, XAML and the rest of the XML family are highlighted the moment they open (brief 0073's Edit Project File makes this daily); `appsettings*.json` and `launchSettings.json` are JSON with comments, so the comments both IDEs accept are not errors; `.http` files are highlighted and their requests are sent with Visual Studio's variables and environments, the response shown in a document; Entity Framework Core migrations are added, applied, removed, scripted and listed through `dotnet-ef` out of process with their output in an "Entity Framework" Output source; and Manage User Secrets opens a project's `secrets.json`, adding `UserSecretsId` first when the project has none. Each action is a command agents reach over MCP with the same schema.

## Contract

**XML.**
- `XML` (id `xml`, name `XML`) on `tree_sitter_xml::LANGUAGE_XML`, for the suffixes `xml`, `csproj`, `vbproj`, `fsproj`, `sqlproj`, `vcxproj`, `proj`, `projitems`, `shproj`, `props`, `targets`, `pubxml`, `user`, `config`, `resx`, `xaml`, `axaml`, `nuspec`, `ruleset`, `runsettings`, `testsettings`, `slnx`, `manifest`, `xsd`, `xsl`, `xslt`, `svg`, `filelists`, `natvis`, `vstemplate`, `xlf`, `xliff`, `wxs`, `wxi`, `edmx`, `dbml`, `plist`, `sitemap`, `wsdl`, `disco`, `storyboard`. `DTD` (id `dtd`) on `LANGUAGE_DTD` for `dtd`, `ent`, `mod`. `.resx` opened as text (Open With > XML (Text) Editor) is XML; the `.resx` editor is unchanged.
- The query (adapted from the crate's, its license line kept) paints element names `@tag`, attribute names `@tag.attribute`, attribute values `@string`, entity and character references `@string.escape`, comments, the XML declaration and processing instructions `@preprocessor`, CDATA markers as keywords and their content as strings, the doctype and DTD declarations; element text keeps the default color. MSBuild's `$(...)` and `@(...)` inside values are part of the string: the grammar has no node for them and painting them would need a second layer, so they are out of scope here.

**JSON with comments.** `FILE_NAME_PATTERNS` (whole file names with one `*`, case-insensitive, checked after the exact `file_names` and before the suffixes) maps `appsettings.json`, `appsettings.*.json`, `launchSettings.json`, `devcontainer.json`, `.devcontainer.json` and `*.code-workspace` to `jsonc`. `servers.json`'s JSON registration gives the same files the `jsonc` language id, so the JSON server accepts comments; the SchemaStore mappings of brief 0050 (`appsettings.json`, `launchSettings.json`) are unchanged.

**`.http` files.**
- `grammars/http` (`tree-sitter-http`, MIT, in-repo because no crate on crates.io writes Visual Studio's format) parses requests separated by `###` lines: a request line (method and URL, or a bare `http(s)://` URL; an optional `HTTP/x`), headers, a blank line and a body; `@name = value` variables; `#` and `//` comments; `{{...}}` references. Generated at build time like Razor (ADR-0012). `HTTP` (id `http`) for `http` and `rest`, with a query painting methods and versions as keywords, URLs and header values as strings, header names as keys, variables and references as variables, separators as doc comments.
- The shell's parser (`http_client.rs`) reads the text itself: requests with their first line, name (`# @name x`), method (GET when absent), URL, headers and body; file variables in order (a later one may reference an earlier one); the request at a line. Substitution of `{{name}}` from, in order: file variables, the selected environment (its `$shared` values under it), request variables `{{req.response.body.$.a.b[0]}}` / `{{req.response.headers.Name}}` from earlier responses this session; dynamic variables `{{$guid}}`, `{{$randomInt min max}}`, `{{$timestamp [offset unit]}}`, `{{$datetime rfc1123|iso8601 [offset unit]}}`, `{{$localDatetime ...}}`, `{{$processEnv NAME}}`, `{{$dotenv NAME}}` (the nearest `.env` up from the file). An unknown variable is an error naming it; nothing is sent.
- Environments: `http-client.env.json` and `http-client.env.json.user` (the user file wins per value) from the `.http` file's folder up to the workspace root, the nearest found; `$shared` is applied under each environment; the selected environment is per session (`eludite.http.select_environment`), the first one by default, none when there is no file.
- Sending runs on a thread of its own with `ureq` 3 over `rustls` (as `eludite-update`, no new HTTP client): the method, headers and body as written, redirects not followed (Visual Studio shows the 3xx), a 100 s timeout, loopback never proxied; the response (status, reason, elapsed, headers, body) is kept for request variables and shown in a document: a file under the system temporary folder (`eludite-http/<file stem>-<request>.response.<ext>`) whose first lines are comments with the status line, the time and the headers, then the body pretty-printed for JSON (`.jsonc`), XML (`.xml`, indented), else as text; Copy and Save are the editor's.
- UI: Tools > HTTP Client > Send Request (the request at the caret of the active `.http` document; `Ctrl+Alt+S`), Tools > HTTP Client > Environment... cycles the environments shown in the status bar. A "Send Request" CodeLens needs `codelens.rs` (another brief's file) and is not added here.
- `eludite.http.send` (`path` and `line` or `name`, or `text` with `line`; `environment` optional; `timeout_ms`): output `status`, `reason`, `elapsed_ms`, `headers`, `body` (up to 256 KB, `truncated`), `response_path`, `url`, `method`. Permission class execute; its escalation hook resolves the request (no network) and raises an agent's call to dangerous when the URL is off the browser policy's allowed origins (loopback, the workspace's launch URLs by default), as `eludite.browser.navigate` does. `eludite.http.environments` (read) lists a file's environments and the selected one; `eludite.http.select_environment` (read class: it changes no file) selects one.

**Entity Framework Core.**
- `eludite.ef.status` (read): whether `dotnet-ef` is available and how (`local`, the nearest `.config/dotnet-tools.json` or `dotnet-tools.json` naming `dotnet-ef`; `global`, `~/.dotnet/tools/dotnet-ef`; `none`), its version from `dotnet ef --version` when available. `eludite.ef.install_tool` (execute; the UI asks first): `dotnet new tool-manifest` when no manifest exists, then `dotnet tool install dotnet-ef` in the solution's folder.
- `eludite.ef.contexts`, `eludite.ef.migrations` (read: they run `dotnet ef dbcontext list --json` / `migrations list --json`, which build the project, so their class is execute), `eludite.ef.add_migration` (`name`, `output_dir`), `eludite.ef.remove_migration` (`force`), `eludite.ef.update_database` (`migration`, `connection`), `eludite.ef.script` (`from`, `to`, `idempotent`, `output`): each with `project` (required), `startup_project` and `context` (optional), execute class. They run `dotnet ef ... --project P --startup-project S --context C --prefix-output` out of process on a thread of their own, with every line in the Output window's Entity Framework source (prefixes stripped), `error:` lines and MSBuild `file(line,col): error CODE: message` lines kept as the result's `errors` and shown in the Error List with their locations, a typed result (`migration` files added, `migrations` with `id`, `name`, `applied`; `contexts` with `name`, `full_name`; `script` text or its path), and cancellation through the job. `dotnet` is the one on `PATH` (`ELUDITE_DOTNET` overrides, for the tests' fake).
- UI: Tools > Entity Framework Core > Add Migration..., Update Database, Remove Last Migration, Generate SQL Script..., List Migrations; each opens one dialog with the project (the startup project's by default), the startup project and the DbContext (listed by `eludite.ef.contexts` off the UI thread) and, for Add Migration, the name; for Generate SQL Script the script opens in an editor tab. When `dotnet-ef` is missing the dialog says so and offers Install (a local tool, after asking).

**Manage User Secrets.**
- `eludite.project.user_secrets` (`project`; execute class: it may edit the project file): reads `UserSecretsId` from the project file; when missing, adds `<UserSecretsId>guid</UserSecretsId>` to the first unconditioned `<PropertyGroup>` with its children's indentation and line ending, keeping every other byte (as `dotnet user-secrets init` does, without running it); then creates `secrets.json` (`{\n}`) when missing under `~/.microsoft/usersecrets/<id>/` (Linux, macOS; `$HOME`) or `%APPDATA%\Microsoft\UserSecrets\<id>\` (Windows), and returns `id`, `path`, `added_id`, `created`. The UI's Workspace context menu item Manage User Secrets on a .NET project runs it and opens the file.

Commit messages: one plain, direct, active-voice line each; no body, no trailers.

## Proving test

- `cargo test -p eludite-editor config_tests` and `dotnet_tests`: XML on a `.csproj` with `$(Prop)` and `@(Item)`, a `web.config`, a XAML window and a props file with a DTD subset; `.http` on a request file with variables; the language table's suffixes and the jsonc file names; every fixture parses with no error node; a 5,000-line `.csproj` parse under 10 ms in release (`assert_budget`).
- `cargo test -p tree-sitter-http`: the corpus replayed, the generator pin.
- `cargo test -p eludite-lsp`: the jsonc language ids for the new names.
- `cargo test -p eludite-commands`: every new schema parses and names its command, two files per command, the classes, input checks, the send hook (loopback execute, off-origin dangerous).
- `cargo test -p eludite http_client`: parsing, variables, environments with `$shared` and `.user`, dynamic variables, request variables, the request at a line, and a send through `eludite.http.send` to an in-process `TcpListener` server with the response document written; `ef_core`: every command against a fake `dotnet` script that records its arguments and prints dotnet-ef's prefixed JSON, the Output source, errors to the Error List; `user_secrets`: the path per OS, init on a temp project keeping its bytes, an existing id reused.
- `cargo fmt --check`; `cargo clippy --all-targets -- -D warnings` on every touched crate.

## Budget

- A 5,000-line `.csproj` parses in under 10 ms in release; highlighting keeps the editor's budgets.
- No UI-thread network or process wait: sending, `dotnet ef` and the tool probes run on threads of their own; the UI gets events.
- No network at startup; `.http` sends only when asked.
- New dependencies: `tree-sitter-xml` 0.7.0 (MIT); `tree-sitter-http` (in-repo, MIT). `ureq` and `getrandom` are already in the build.

## Exit criterion

The proving tests pass here; `cargo fmt --check` and clippy are clean on the touched crates; the report lists what was run, what was not, and the Integration notes for `README.md`, `CLAUDE.md` and `docs/briefs/README.md`.

## Out of scope

An XML language server, MSBuild completion and schema validation; painting `$(...)` inside values; the Send Request CodeLens (`codelens.rs`); `.http` features beyond Visual Studio 17.12's documented set (no scripting, no `< file` bodies beyond reading the file as is, no gRPC or WebSocket requests); Azure Key Vault and other secret providers in `http-client.env.json`; EF Core reverse engineering (`dbcontext scaffold`), bundles and compiled models; EF6; Manage User Secrets for .NET Framework projects' `web.config` builders.
