# Brief 0051: The web package UI, `package.json` scripts as run targets, and workspaces

Status: open
Phase: 2 (PLAN.md section 7, the Web row: "npm, pnpm, yarn, bun with a package UI like NuGet's; `package.json` scripts as run targets; workspaces")
Plan reference: PLAN.md sections 2 (principles 1, 2, 3, 4, 5, 12), 4.2 (the Workspace window), 4.7 (the NuGet window this one mirrors), 5.1, 5.4, 7 (the Web row), 8 (Visual Studio names: the npm node under Dependencies, Task Runner Explorer for scripts), 9, 10 (Phase 2)
Related ADRs: ADR-0002, ADR-0003
Depends on: brief 0048 (the Manage NuGet Packages window: its tabs, list, detail pane and the Dependencies node are the pattern and the shared widgets), brief 0041 (the terminal: scripts run in it), brief 0050 (Node located; `package.json` with its schema), brief 0035 (Test Explorer, for `test` scripts shown as a run target, not as tests).

## Goal

A project with a `package.json` (an ASP.NET project's `ClientApp` or `wwwroot`, a Vite project, a folder workspace) shows an npm node under Dependencies in the Workspace window (Visual Studio's name) with its dependencies and devDependencies, their installed and wanted versions, and a glyph on a package with a known vulnerability (from the registry's audit endpoint) or missing from `node_modules`. Manage Packages on that node opens the same window brief 0048 built, with Browse (the npm registry's search), Installed, Updates and Consolidate (across the workspaces of a monorepo), and Install, Update and Uninstall run the project's package manager (npm, pnpm, yarn or bun, detected from the lockfile, `packageManager` in `package.json`, or the setting) in the integrated terminal, so the person sees exactly what ran and can answer prompts; the package manager's registry configuration (`.npmrc`, scoped registries, auth tokens) is read as the manager reads it and never bypassed. `package.json` scripts appear in the Workspace under an npm Scripts node and in Task Runner Explorer (Visual Studio's window for this), run in the terminal with Run, Debug (under Node through brief 0038's adapter, `pwa-node` launch) and the bindings Visual Studio offers (Before Build, After Build, Clean, Project Open) persisted in `.eludite/tasks.json`, so a `build` script can run before F5. Workspaces (`workspaces` in `package.json`, pnpm's `pnpm-workspace.yaml`) list each package with its own scripts and dependencies, and a script can run in all of them. Agents use `eludite.npm.*` (`packages`, `search`, `install`, `uninstall`, `update`, `scripts`, `run_script`, `audit`) with the same semantics, under the policy's `npm` object (changes and running scripts `prompt` by default).

## Contract

- **Detection.** The manager from `packageManager` in `package.json`, else the lockfile present, else the setting, else npm; the registry and auth from `.npmrc` as the manager reads them; nothing contacts a registry at startup (audit only on the window's Installed tab, `npm.auditOnOpen`, or `eludite.npm.audit`).
- **The window.** Brief 0048's window with the npm provider: Browse searches the registry with the debounce, Installed lists declared and installed versions with the glyphs, Updates lists wanted and latest, Consolidate works across workspaces; Install, Update and Uninstall run the manager's command in the integrated terminal (a tab named after the package) and the node refreshes when the command exits and the lockfile changed; a failed command stays visible in the terminal.
- **Scripts.** The Scripts node and Task Runner Explorer list every script with its command; Run opens a terminal tab and runs `<manager> run <script>` in the package's folder; Debug launches `node` under js-debug with the script's command (the report says how `pwa-node` receives it); bindings persist in `.eludite/tasks.json` and run at the bound moments with their output in the terminal and a line in the Output window; a bound script that fails before a build fails the build with the Error List row.
- **Workspaces.** Each package of a workspace is a node with its own scripts and dependencies; "Run in all workspaces" runs the manager's workspace command (`npm run -ws`, `pnpm -r run`, `yarn workspaces foreach`, `bun run --filter '*'`) in one terminal.
- **Agents.** `packages`, `search`, `scripts` and `audit` are reads; `install`, `uninstall`, `update` and `run_script` are `execute` under `npm.change` and `npm.run` (`prompt` by default, "Allow for this session" as brief 0041); `run_script` with `wait_ms` answers the exit code and the last 50 lines; every change is audited with the package and the command line.
- The UI thread never waits on a registry, a lockfile parse or a process; no `node` or manager process at startup; the manager's own output is the record (Eludite never rewrites `package.json` itself).
- Commit messages: one plain, direct, active-voice line each; no body, no trailers.

## Proving test

- `crates/npm`: the four lockfiles and the workspace fixtures, the manager detection order, the registry client against the loopback fake (search, packuments, audit, scoped registry with a token from `.npmrc` sent only to that registry), the command lines per manager, the bindings file round trip.
- `crates/eludite` headless tests (fake registry, a fake manager script on PATH that records its arguments and writes a lockfile change): the npm node with versions and glyphs, Manage Packages opens the shared window with the npm provider and Browse, Installed, Updates and Consolidate across two workspaces, Install runs the manager in a terminal tab and the node refreshes, Uninstall and Update, the Scripts node and Task Runner Explorer list the scripts, Run opens the terminal and runs the command in the package's folder, Debug starts a session with the fake js-debug adapter, a Before Build binding runs before a build and its failure fails the build, Project Open runs its binding once, Run in all workspaces, an agent's `packages` matches the node, `install` asks under `prompt`, `run_script` with `wait_ms` answers the exit code and lines, nothing contacts the fake registry before the window opens (counted).
- Real: with the pinned npm from brief 0050's cache or the system `npm` (present here), `npm install` of the Vite fixture in a copy through the window's path and `npm run build` through Run, under Xvfb; the screenshots in the report.

## Budget

- The npm node renders within 100 ms of the Workspace opening for a 200-dependency `package.json` with its lockfile (parsed off-thread, cached per lockfile mtime); the Installed tab under 200 ms from the cache plus the registry's time.
- A script's first terminal line within 300 ms of Run (the terminal's own budget); the window keeps frame p99 under 8 ms with 500 results (`assert_budget`).
- No new Rust dependency (`ureq` is in the build); a YAML crate is not added (see the lockfile note).

## Exit criterion

1. `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` green with the real npm test running here; `dotnet build` and `dotnet test` unchanged.
2. The report records the budget numbers, the manager command table, the provider trait as shipped with brief 0048's window, how Debug reaches `pwa-node`, and what Vitest, Jest and Playwright adapters can reuse.
3. `CLAUDE.md`, `README.md` if touched, `corpus/README.md`, the briefs index and the MCP tool and resource lists match the repository.

## Out of scope

- Vitest, Jest and Playwright test adapters (their own brief on the Test Explorer); Vue, Svelte and Astro servers; Tailwind; publishing packages; `npx` and `dlx` runners beyond what scripts invoke; Windows and macOS runs beyond CI.
